## 一、先認識幾個 GitHub 名詞

| 名詞 | 白話解釋 |
| --- | --- |
| 儲存庫（repository、repo） | 專案的資料夾，放在 GitHub 上，大家共用 |
| 複製（clone） | 把 GitHub 上的儲存庫下載到自己電腦，只要做一次 |
| 分支（branch） | 從主線複製出來的「平行世界」，在這裡改壞了也不會影響別人 |
| `main` | 主線分支，只放穩定、可以展示的版本 |
| 提交（commit） | 幫目前的修改「存檔」並寫一句說明 |
| 推送（push） | 把自己電腦上的提交上傳到 GitHub |
| 拉取（pull） | 把 GitHub 上別人的新修改下載到自己電腦 |
| Pull Request（PR） | 「請大家看看我的修改，沒問題就併進 `main`」的申請單 |
| 合併（merge） | 把分支的修改併進 `main` |
| 衝突（conflict） | 兩個人改到同一個檔案的同一個地方，Git 不知道要留哪一個 |
| Issue | 待辦事項卡片，一張卡寫一件工作 |

**為什麼要開分支、發 PR，而不是直接改 `main`？**
三個人同時改 `main` 很容易互相蓋掉。每人在自己的分支做事，做完再透過 PR 讓別人看過才合併，`main` 就會一直保持可以展示的狀態。

## 二、第一次設定（每人只要做一次）

### 2-1 張○誠：儲存庫擁有者的設定

**1. 邀請組員**

GitHub 儲存庫頁面 → `Settings` → `Collaborators` → `Add people`，輸入呂、余的 GitHub 帳號。

**2. 保護 `main` 分支**

`Settings` → `Rules` → `Rulesets` → `New ruleset` → `New branch ruleset`：

1. `Ruleset name` 填 `保護 main`，`Enforcement status` 選 `Active`。
2. `Target branches` → `Add target` → `Include default branch`（也就是 `main`）。
3. 勾選：
   - `Restrict deletions`（不能刪除 `main`）
   - `Block force pushes`（不能強制覆蓋歷史）
   - `Require a pull request before merging`，`Required approvals` 設 `1`
4. `Bypass list`（誰可以略過規則）→ `Add bypass` → 選 `Repository admin`，模式選 **`For pull requests only`**。
5. 按 `Create`。

**擁有者自己的修改也要審查嗎？**

- GitHub **不允許自己審查自己的 PR**。如果沒有設定第 4 步，張○誠的每個 PR 都要等呂或余按 `Approve` 才能合併。
- 設定第 4 步之後：張○誠**還是要開分支、發 PR**（不能直接推送到 `main`），但合併時可以勾選略過審查，直接合併。
- **建議的用法**：平常仍然請組員審查（照第五節的規則），只有在緊急修正、或組員兩天內都沒回覆時才略過，並在 PR 留言說明原因。這樣 `main` 一樣有紀錄可查，出問題時也能退回。
- 為什麼選 `For pull requests only` 而不是 `Always`：選 `Always` 等於允許擁有者直接推送到 `main`，跳過 PR，就沒有預覽網址可以先測試，也比較容易誤推。

**3. 建立看板與 Issue**

1. 儲存庫頁面 → `Projects` → `New project` → 選 `Board`，欄位用「待辦／進行中／審查中／完成」。
2. 把第八節的工作清單，一項建一張 Issue，指派給負責人。

**4. 建立 Firebase 專案**（免費的 Spark 方案，不用綁信用卡）

1. 到 Firebase 主控台 → `新增專案`，名稱例如 `teachbot-arena`。Google Analytics **不要啟用**（少蒐集一份資料）。
2. `建構` → `Authentication` → `開始使用` → `登入方式` → 啟用 `電子郵件/密碼`。
3. `Authentication` → `使用者` → `新增使用者`，先建立測試帳號，代號用不存在的班級 `999`（例如 `99901@teachbot.example`、`99902@teachbot.example`），和真實學生分開。
4. `建構` → `Firestore Database` → `建立資料庫` → 位置選 `asia-east1`（台灣）→ 選**正式版模式**（預設全部拒絕，比較安全）。
5. `專案設定` → `一般` → `你的應用程式` → 點網頁圖示 `</>` → 註冊應用程式，畫面會出現 `firebaseConfig`。這是公開設定，交給 Claude Code 放進 `public/js/firebase-config.js`。
6. `專案設定` → `服務帳戶` → `產生新的私密金鑰`，會下載一個 JSON 檔：
   - **這個檔案不要放進專案資料夾**，也不要傳給任何人。
   - 打開檔案，把 `project_id`、`client_email`、`private_key` 三個值填到自己的 `.env` 和 Vercel 後台（第 5 步）。
   - 填完後把 JSON 檔移到安全的地方保存，或直接刪除（需要時可以重新產生）。
7. 安全規則：`Firestore Database` → `規則` 分頁，貼上 `firestore.rules` 的內容 → `發布`。之後規則有修改，也要重新貼上並發布。

**5. 建立 Vercel 專案**

1. 用 GitHub 登入 Vercel → `Add New` → `Project` → 匯入本儲存庫，`Framework Preset` 選 `Other`。
2. `Settings` → `Environment Variables`，依 `.env.example` 填入：`GEMINI_API_KEY`、`FIREBASE_PROJECT_ID`、`FIREBASE_CLIENT_EMAIL`、`FIREBASE_PRIVATE_KEY`、`AI_DAILY_LIMIT_PER_STUDENT`。
   - **`USE_FAKE_DB` 不要在 Vercel 設定**，正式網站一定要連線真的資料庫。
3. 假設：公開儲存庫的 PR 會自動產生預覽網址；如果組員的 PR 沒有出現預覽網址，改成合併後再看正式網址。

**6. 申請正式用的 Gemini 金鑰**

到 Google AI Studio 用自己的帳號建立金鑰，**只填在 Vercel 後台**。學生不需要任何金鑰。

### 2-2 每位組員都要做

## 三、每次開發的標準流程

**口訣：先拉、開分支、做、看狀態、存檔、推、發 PR。**

以呂○蓁要做「拍照上傳畫面」為例：

**1. 回到 `main` 並拿到最新版本**

```powershell
git switch main
```

```powershell
git pull
```

為什麼：從最新的版本開始做，之後合併比較不會衝突。

**2. 開一個新分支**

```powershell
git switch -c feat/scan-upload
```

分支命名規則：

| 開頭 | 用途 | 範例 |
| --- | --- | --- |
| `feat/` | 新功能 | `feat/scan-upload`、`feat/battle-hp-bar` |
| `fix/` | 修正錯誤 | `fix/tutor-timeout` |
| `art/` | 美術素材 | `art/robot-dumbbot` |
| `docs/` | 文件 | `docs/meeting-1203` |

**3. 用自己的 AI 工具開發**（見第四節）

**4. 在本機測試**：確認畫面能打開、功能能用。

**5. 看看改了哪些檔案**

```powershell
git status
```

檢查清單：
- 有沒有出現 `.env` 或任何金鑰檔？**有的話不要提交**，先找張○誠。
- 有沒有改到不是自己負責的檔案？有的話先確認是不是必要的。

**6. 把要提交的檔案加入**（一個一個指定，不要用 `git add .`）

```powershell
git add public/js/scan.js public/css/scan.css
```

**7. 存檔並寫說明**

```powershell
git commit -m "新增題目拍照上傳畫面"
```

**8. 推送到 GitHub**

```powershell
git push -u origin feat/scan-upload
```

**9. 在 GitHub 開 Pull Request**

1. 推送後打開儲存庫頁面，會看到黃色提示 `Compare & pull request`，點下去。
2. 標題寫做了什麼，內容照這個格式填：

   ```
   ## 做了什麼
   - 新增拍照／選擇圖片上傳的畫面
   - 圖片上傳前先縮小，避免檔案太大

   ## 怎麼測試
   1. 打開預覽網址的「上傳題目」頁
   2. 選一張題目照片，確認畫面有出現預覽

   ## 相關 Issue
   Closes #5
   ```

3. 右側 `Reviewers` 指定審查者（見第五節）。
4. 寫 `Closes #5` 的話，PR 合併後第 5 號 Issue 會自動關閉。

**10. 等待審查**：審查者會留言或按 `Approve`。要修改就在**同一個分支**繼續改、commit、push，PR 會自動更新。

**11. 合併**：通過後按 `Squash and merge` → `Confirm`，再按 `Delete branch`。

**12. 所有人更新自己的 `main`**

```powershell
git switch main
```

```powershell
git pull
```

**分支做很久了，想拿到 `main` 的新東西？**

```powershell
git switch feat/scan-upload
```

```powershell
git merge main
```

> 時程很短，**分支最好 1～2 天內就發 PR 合併**，不要一次累積太多修改。

## 四、三種 AI 開發工具的操作方式

### 共同原則

- 儲存庫裡的 `AGENTS.md` 寫了全組的共同規則，**每次開始新任務前，都要讓 AI 先讀它**。
- 前端呼叫後端**一律透過 `public/js/api.js`**，不要在自己的畫面裡直接寫後端網址。
- AI 寫完的程式，一定要自己打開畫面測過，再 commit。
- AI 想要 commit 或 push 時，先讓它執行 `git status`，自己看過檔案清單再同意。
- 不要讓 AI 修改不是自己負責的資料夾；如果 AI 說「需要改別人的檔案」，先在群組討論。

### 4-1 張○誠：Claude Code

1. 用 Claude Code 打開 `C:\Projects\team-work`。
2. 儲存庫裡的 `CLAUDE.md` 已經寫了 `@AGENTS.md`，Claude Code 會自動讀取共同規則。
3. 常用的請求方式：
   - 「從 main 開一個 feat/dumbbot-options 分支，依照 docs/合作分工表.md 第七節的介面約定，實作笨笨機器人產生 A、B 兩種解法的後端。」
   - 「執行 git status 給我看，我確認後再 commit。」
   - 「用 gh 幫我開 Pull Request，審查者指定呂○蓁的帳號。」（需先安裝 GitHub CLI 並執行 `gh auth login`）
4. 審查別人的 PR 時，可以請 Claude Code：「幫我看 PR #8 有沒有把金鑰或學生資料放進程式、有沒有用 innerHTML 放使用者輸入。」

### 4-2 呂○蓁：Antigravity

1. 用 Antigravity 開啟資料夾 `C:\Projects\team-work`。
2. 每次開始新任務時，先對 Agent 說：「請先閱讀 AGENTS.md 與 docs/合作分工表.md 第七節，並遵守裡面的規則。」
   - 假設：若 Antigravity 有工作區規則（Rules）的設定，把同一句話加進去，就不用每次重講；實際位置以 Antigravity 的介面為準。
3. 開分支、commit、push 可以用左側的「原始碼控制（Source Control）」面板，也可以在內建終端機輸入第三節的指令。
4. **提示詞可以先在 Google AI Studio 的網頁上調**：直接貼上提示詞和題目測試，效果滿意再寫進 `prompts/` 資料夾的 `.md` 檔。這樣不用等後端完成就能開始做。
5. 測試題目照片放在專案裡的 `test-photos/` 資料夾（已列入 `.gitignore`，不會被上傳），**不要放在其他會被提交的位置**（照片可能拍到姓名或學校資訊）。

### 4-3 余○靜：ChatGPT 與 Codex

**用 ChatGPT 畫美術素材**

1. 先和組員確認角色設定，再請 ChatGPT 產生圖片；同一個角色用同一段描述，風格才會一致。
2. **不要要求模仿現有的卡通角色**（例如「畫得像某某動畫的機器人」），避免著作權問題。
3. 每個機器人準備這些表情或動作：`idle`（待機）、`happy`（開心）、`confused`（困惑）、`attack`（攻擊）、`hurt`（受傷）。
4. 素材規格：

   | 項目 | 規格 |
   | --- | --- |
   | 格式 | 透明背景 PNG，或 SVG |
   | 大小 | 每張 200 KB 以內（平板載入才會快） |
   | 檔名 | 英文小寫與連字號，例如 `dumbbot-confused.png` |
   | 位置 | `public/assets/robots/`、`public/assets/ui/` |

**用 Codex 寫程式**（兩種方式擇一）

- **方式 A：Codex 雲端（不用在電腦上操作 Git，最簡單）**
  1. 在 ChatGPT 的 Codex 頁面連結 GitHub 帳號，並選擇本儲存庫（授權畫面請自己確認權限範圍）。
  2. 輸入任務，例如：「依照 AGENTS.md 的規則，在 public/js/battle.js 做出血量條元件，資料先用 public/js/mock-data.js 的假資料，對戰邏輯一律呼叫 public/js/battle-rules.js。」
  3. Codex 做完後，檢查它列出的修改內容，再按「建立 PR」。
  4. 到 GitHub 的 PR 頁面看預覽網址，確認畫面正確。

## 六、遇到合併衝突怎麼辦

**情況**：PR 頁面出現 `This branch has conflicts that must be resolved`。

**簡單的衝突**（GitHub 網頁上就能處理）

1. 點 `Resolve conflicts`。
2. 檔案中會出現這樣的標記：

   ```
   <<<<<<< feat/scan-upload
   你的版本
   =======
   main 上的版本
   >>>>>>> main
   ```

3. 改成正確的內容，刪掉 `<<<<<<<`、`=======`、`>>>>>>>` 三行標記，按 `Mark as resolved` → `Commit merge`。

**複雜的衝突**（在自己電腦處理）

```powershell
git switch feat/scan-upload
```

```powershell
git merge main
```

接著請自己的 AI 工具：「幫我解決這次合併衝突，兩邊的功能都要保留，改完先讓我測試。」測試沒問題後：

```powershell
git status
```

```powershell
git add 有衝突的檔案
```

```powershell
git commit -m "合併 main 並解決衝突"
```

```powershell
git push
```

**怎麼減少衝突**：每人只改自己的資料夾、分支 1～2 天內合併、每天開工前先 `git pull`。

## 七、介面約定（第一週前 3 天定案）

> 三個人分別用不同的 AI 工具開發，**資料格式一定要先約好**，最後才接得起來。以下是草案，第一週會議討論後定案；之後要修改，必須三人都同意，並更新這一節。

### 7-1 預留未來擴充的四個設計

1. **前端只透過 `public/js/api.js` 呼叫後端**（7-4）。以後換後端或加連線，只改這個檔案。
2. **資料格式固定**（7-2）。以後資料要搬家，欄位名稱都不用改。
3. **對戰規則寫成獨立的 `public/js/battle-rules.js`**（7-5），不直接操作畫面。以後連線時，同一份規則可以搬到後端當裁判。
4. **對電腦對戰也用「對戰狀態」物件記錄**（7-5），格式和未來的連線房間相同。

### 7-2 Firestore 資料結構

**使用者 `users/{uid}`**

```json
{
  "studentCode": "50101",
  "classId": "501",
  "robotName": "閃電號",
  "robotSkin": "blue"
}
```

`robotName`、`robotSkin` 只能從預設清單挑選。

**題庫 `questions/{questionId}`**（學生只能讀自己的）

```json
{
  "ownerUid": "Firebase 帳號 ID",
  "classId": "501",
  "text": "一桶油有 3/4 公升，平分給 3 人，每人分到幾公升？",
  "grade": 6,
  "unit": "分數除法",
  "difficulty": 2,
  "misconception": "除以整數時，分子和分母同時除",
  "createdAt": "伺服器時間"
}
```

**答案 `answers/{questionId}`**（前端完全不能讀，只有後端能讀）

```json
{
  "answer": "1/4",
  "expression": "3/4 ÷ 3"
}
```

**題目草稿 `drafts/{draftId}`**（前端完全不能讀；確認題目後建立，收錄進題庫後刪除）

```json
{
  "ownerUid": "Firebase 帳號 ID",
  "text": "題目文字",
  "grade": 6,
  "unit": "分數除法",
  "difficulty": 2,
  "answer": "1/4",
  "expression": "3/4 ÷ 3",
  "tutorSolved": false,
  "wrongOption": "B",
  "misconception": "除以整數時，分子和分母同時除"
}
```

**AI 用量 `usage/{uid}_{YYYYMMDD}`**（前端完全不能讀寫，後端用來限制每人每天的呼叫次數）

```json
{ "count": 12 }
```

**電腦題庫 `api/_data/computer-bank.json`**（只有後端讀取；儲存庫公開，所以只放示範題目）

```json
[
  {
    "questionId": "cpu_01",
    "text": "題目文字",
    "grade": 5,
    "unit": "小數乘法",
    "difficulty": 1,
    "answer": "2.4"
  }
]
```

### 7-3 答案格式

| 類型 | 寫法 | 範例 |
| --- | --- | --- |
| 整數 | 數字 | `12` |
| 小數 | 數字 | `0.25` |
| 分數 | 分子/分母 | `3/4` |
| 帶分數 | 整數 空格 分子/分母 | `1 1/2` |

後端會把答案換算成數值再比對，所以 `1/2`、`2/4`、`0.5` 都算對（是否接受未約分的答案，第一週討論）。

### 7-4 前端 `api.js` 與後端 API

**前端一律呼叫 `api.js` 提供的函式**，`api.js` 再呼叫後端，並自動在標頭帶上登入憑證（`Authorization: Bearer <Firebase ID Token>`）。`USE_FAKE_DB=1` 或後端還沒完成時，`api.js` 可以改回傳 `mock-data.js` 的假資料。

| `api.js` 函式 | 後端網址與 `action` | 負責人 | 送出 | 回傳 |
| --- | --- | --- | --- | --- |
| `api.login(code, password)` | Firebase Authentication | 張 | 代號、密碼 | 使用者資料 |
| `api.scan(image)` | `/api/problem`、`scan` | 呂 | 縮小後的圖片 base64 | `{ text }` |
| `api.confirmProblem(text)` | `/api/problem`、`confirm` | 呂 | 學生確認後的文字 | `{ draftId, grade, unit, difficulty }`，不適合的題目回 `{ rejected: true, reason }` |
| `api.tutor(draftId, message)` | `/api/tutor` | 呂 | 學生的話或答案 | `{ reply, solved }` |
| `api.dumbbotChallenge(draftId)` | `/api/dumbbot`、`challenge` | 張 | — | `{ text, options: { A, B } }` |
| `api.dumbbotJudge(draftId, choice, explanation)` | `/api/dumbbot`、`judge` | 張 | 選項、說明 | `{ pass, feedback, questionId }` |
| `api.listMyQuestions()` | 直接讀 Firestore（加 `limit()`） | 張 | — | 自己的題庫（不含答案） |
| `api.computerAttack(usedIds)` | `/api/battle`、`computerAttack` | 張 | 這場已用過的電腦題目 | `{ questionId, text, difficulty }`（不含答案） |
| `api.checkAnswer(questionId, answer)` | `/api/battle`、`answer` | 張 | 電腦題目編號、學生答案 | `{ correct }` |

**重要規則**

- 學生答案的對錯（引導機器人的 `solved`、對戰的 `correct`）一律由**程式比對**，不交給 AI 判斷。
- AI 只負責：辨識題目、產生引導問題、產生笨笨的兩種解法、評判學生的說明。
- 每個呼叫 AI 的後端，都要先經過 `api/_lib/` 的用量檢查；超過每日上限時回 `{ limited: true }`，畫面顯示「今天的 AI 次數用完了，明天再來」。

### 7-5 對戰狀態與 `battle-rules.js`

**對戰狀態物件**（對電腦對戰存在瀏覽器記憶體中；未來連線時，同樣格式存成 Firestore 的房間資料）

```json
{
  "mode": "computer",
  "players": ["我的 uid", "computer"],
  "hp": { "我的 uid": 5, "computer": 5 },
  "attacker": "我的 uid",
  "phase": "choosing",
  "currentQuestion": { "questionId": "q_0001", "text": "題目文字", "difficulty": 2 },
  "deadline": 1764300000000,
  "usedQuestionIds": [],
  "round": 1,
  "winner": null
}
```

`phase` 的值：`choosing`（出題中）→ `answering`（解題中）→ `finished`（結束）。未來連線時再加上 `waiting`（等人加入）。

**`battle-rules.js` 提供的函式**（只計算、不操作畫面，方便測試）

| 函式 | 用途 |
| --- | --- |
| `createBattle(myUid)` | 建立新的對戰狀態 |
| `chooseQuestion(state, question)` | 出題，進入解題階段並設定倒數 |
| `applyResult(state, correct)` | 依答對或答錯扣血、換回合、判定勝負 |
| `computerAnswers(difficulty)` | 電腦依難度用機率決定答對與否（★ 70%、★★ 50%、★★★ 30%） |
| `timeLimit(difficulty)` | 回傳解題秒數（★ 60、★★ 90、★★★ 120） |

### 7-6 共用程式（張○誠第 1 週第 3 天前提供）

| 檔案 | 用途 |
| --- | --- |
| `api/_lib/gemini.js` | 呼叫 Gemini 的共用函式，其他人不用各自處理金鑰 |
| `api/_lib/firebase.js` | 連線 Firestore、驗證登入；`USE_FAKE_DB=1` 時改用假資料 |
| `api/_lib/answer.js` | 答案格式換算與比對、算式驗算（不使用 `eval`） |
| `api/_lib/usage.js` | 每位學生每天的 AI 呼叫次數限制 |
| `public/js/api.js` | 前端呼叫後端的唯一入口 |
| `public/js/mock-data.js` | 前端假資料（題庫、對戰狀態），讓呂、余不用等後端就能做畫面 |

## 十、禁止事項與出事時的處理

**絕對不要做**

- 直接推送到 `main`（包括儲存庫擁有者）。
- 把 `.env`、金鑰、密碼貼進程式、Issue、PR 或群組。
- 在程式、範例資料或測試資料中寫入學生真實姓名，一律用代號（例如 50101）。
- 把學生作業的真實照片上傳到儲存庫。
- 把使用者輸入直接放進 `innerHTML`（請用 `textContent`）。
- 沒討論就安裝大型套件。
- 沒告知就修改別人負責的資料夾。

**不小心把 `.env` 或金鑰推上去了**

1. **立刻**到 Google AI Studio（或 Firebase 後台）**刪除那把金鑰，重新建立一把**。這一步最重要，因為公開儲存庫的內容可能已經被別人看到。
2. 通知張○誠。
3. 從 Git 移除追蹤（檔案還會留在電腦上）：

   ```powershell
   git rm --cached .env
   ```

   ```powershell
   git commit -m "移除誤傳的環境變數檔"
   ```

4. 注意：舊的 commit 紀錄裡還看得到內容，所以第 1 步撤銷金鑰一定要做。要清除歷史紀錄需要改寫歷史，**先備份整個資料夾**，再和張○誠一起處理。

**部署前檢查（第 3 週，張○誠負責）**

1. 程式與靜態檔中沒有測試金鑰或機敏字串。
2. `git status` 與 commit 紀錄中沒有 `.env` 或機敏檔案。
3. Vercel 的環境變數已設定，建置紀錄沒有印出環境變數；Vercel 上沒有設定 `USE_FAKE_DB`。
4. Firestore 安全規則沒有 `allow read, write: if true`。
5. 在 GitHub 建立版本標籤（`Releases` → `Draft a new release`），保留上一個穩定版本，出問題時可以退回。
